# eLogbook

Electronic logbook for scientific experiments.
Angular 22 (standalone, signals, zoneless) + Angular Material 3 + Tiptap (ProseMirror).

Licence: [MIT](LICENSE).

This is a monorepo: two apps, each with its own `package.json`, tied together by npm workspaces at the root
(one `npm install`, one lockfile, one set of scripts).

| Folder                          | What it is                                                                                                                                                                      |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`frontend/`](frontend)         | The Angular app. It talks to the API for everything (sign-in, logbooks, entries, pins); nothing is stored in the browser except the session token and your appearance settings. |
| [`backend/`](backend/README.md) | The NestJS REST API on PostgreSQL: sign-in (JWT), logbooks, members, entries, version history, pins, sample content. It decides who may do what and tells the app.              |

```bash
nvm use                  # Node 24 (see .nvmrc); needs Node ^22.22.3 or ^24.15
npm install              # installs both apps

npm run up               # OR everything in Docker with hot reload: frontend, API and PostgreSQL (see "Run it all in Docker")
npm run setup:backend    # once, to run without Docker: PostgreSQL (Docker) and backend/.env with a random JWT_SECRET
npm start                # frontend (http://localhost:4300) and API (http://localhost:3000/api/v1, docs at /api/docs) together
npm run start:frontend   # or only one of them
npm run start:backend

npm test                 # unit tests of both apps (the frontend runs in headless Chrome: set CHROME_BIN to your Chrome, e.g. on macOS
                         # "/Applications/Google Chrome.app/Contents/MacOS/Google Chrome")
npm run test:e2e         # API tests against PostgreSQL (run db:up first)
npm run lint             # both apps
npm run build:pages      # the frontend as GitHub Pages builds it
npm test -w frontend     # (or any script of one app: -w frontend / -w backend) Vitest in Chrome, in watch mode
```

Try it with **sample logbooks**: the **Add sample logbooks** button (next to "All logbooks") creates a set of
realistic logbooks for you: one detailed three-day LoKI SANS beamtime (run tables, sample blocks, checklists, a
shear-cell schematic, a detector image, an I(Q) plot, fit results, a leak incident, handover notes and a version
history) plus a dozen smaller ones with different roles (owner / editor / viewer) and access levels, so the list,
search and table view have something to show. **Remove sample logbooks** deletes exactly those again, and nothing
else. They are personal (nobody else sees yours) and the figures and numbers are illustrative, not real
measurements. The content lives in `backend/src/demo/`; the API can switch the feature off (`DEMO_ENABLED=false`).

Create an account on the sign-in page, or, with the API's seed command (`npm run seed -w backend`), sign in with
one of the demo accounts (password `demo1234`): Anna Lindqvist, Jon Carter or Mei Tanaka. Share a logbook with
another account's email address to try the permissions.

## Roles: who can do what

Every logbook has members, and each member has one role. (The person responsible for the logbook is its **owner**,
shown in the logbook's `owner` field; they are always also a member with the owner role.)

|                                                                                                    | Viewer | Editor | Owner |
| -------------------------------------------------------------------------------------------------- | :----: | :----: | :---: |
| Open the logbook, read its entries and their version history                                       |   ✓    |   ✓    |   ✓   |
| Export / print, and pin entries (pins are personal)                                                |   ✓    |   ✓    |   ✓   |
| Add entries and edit them (title and text, saved automatically)                                    |        |   ✓    |   ✓   |
| Save a version, restore an older version                                                           |        |   ✓    |   ✓   |
| Delete an entry                                                                                    |        |        |   ✓   |
| Change the title and description                                                                   |        |        |   ✓   |
| Change who has access and with which role, and the general access (private / open to the facility) |        |        |   ✓   |
| Delete the logbook (with all its entries and history)                                              |        |        |   ✓   |

- **Handing a logbook over:** an owner changes the member list so that someone else is an owner (and changes or
  removes themselves). The logbook always needs at least one owner. The new person can be someone who has not signed
  up yet; they find the logbook when they do.
- **General access** can be _private_ (only the people listed) or _open to the facility_: then everyone signed in can
  read it, as a viewer, without being listed. Nobody gains more than that by it.
- **Administrators** (the emails in the API's `ADMIN_EMAILS`) get no extra access to read or edit. They may delete a
  logbook or entry that they can already open.
- **Sample logbooks** follow the same roles, are personal to the person who added them, and are removed all at once
  with "Remove sample logbooks".
- The rules are written once, in `backend/src/casl/ability.ts`, and enforced by the API on every request. The app only
  shows or hides buttons using what the API tells it (`myRole`, `canWrite`, `canConfigure`, `canDelete`).

Each app has its own dependencies and scripts and can be run alone (`npm run <script> -w frontend`).

## Run it all in Docker

One file, `docker-compose.yaml`, starts everything with your code mounted, so saving a file reloads it:

```bash
npm run up           # = docker compose up --build   (add -d to run in the background)
npm run down         # stop everything (the database keeps its data in a Docker volume)
```

| Service    | Where                                                    | What happens when you edit code                                                 |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------------------------------- |
| `frontend` | http://localhost:4300                                    | the Angular dev server rebuilds and the browser reloads                         |
| `backend`  | http://localhost:3000/api/v1 (docs at `/api/docs`)       | NestJS recompiles and restarts                                                  |
| `db`       | localhost:5433 (user, password and database: `elogbook`) |                                                                                 |
| `deps`     | (runs first, then exits)                                 | installs dependencies; runs again when a `package.json` or the lockfile changes |

- Dependencies are installed for Linux into Docker volumes; your own `node_modules` are not used inside the containers
  (and need not exist). The first start takes a minute or two for that.
- File watching uses polling, because file events do not reliably cross from macOS or Windows into a container.
- The API gets its settings from the compose file (a development-only `JWT_SECRET`), not from `backend/.env`.
- Demo accounts: `docker compose exec backend npm run seed -w backend`. Logs: `docker compose logs -f backend`.
- Run either this or `npm start`, not both: they use the same ports.

```

├── theme/                    generated Material colour palettes (used by styles.scss; every colour variable is listed in COLORS.md)

    │   ├── auth/                 AuthService (abstract), ApiAuthService (sign-in against the API), HTTP interceptor, route guard, CurrentUserService

    │   │                         and ProposalRepository (proposals / samples; fixed demo data until a proposal system is connected)
    │   └── theme/                light / dark ThemeService
    ├── features/
    │   ├── logbooks/             logbook-list/, logbook-card/, logbook-table/, member-avatars/, pinned-entries/, no-results/, logbook-filters.ts, new-logbook-dialog/,
    │   │                         delete-logbook-dialog/ + LogbooksStore (root), delete-logbook service
    │   ├── logbook/              logbook-page/ (entry list), no-entry-selected/ + EntriesStore (page-scoped)
    │   ├── entry/                entry-page/, delete-entry-dialog/ + EntryAutosave (component-scoped)
    │   ├── editor/               rich-text-editor/, editor-toolbar/, insert-sample-dialog/,
    │   │                         Tiptap extensions, ImageService
    │   ├── history/              history-panel/
    │   ├── sharing/              share-dialog/
    │   ├── print/                print-page/
    │   └── auth/                 login-page/ (sign in and sign up)
    └── shared/                   logbook-tags/, prompt-dialog/, table-popover/ (hover card), truncated/ and highlight/ (directives: detect cut-off text, mark search words), user-controls/ (the account icon)
```

Conventions

- **One folder per component**, holding the same four files: `name.ts`, `name.html`, `name.scss` and
  `name.spec.ts`. No inline templates or styles. Code that is not a component (stores, services,
  directives, pure functions) sits next to its feature's component folders with its own `.ts` and
  `.spec.ts`. The root component `app.*` lives directly in `frontend/src/app`.
- Standalone components, `OnPush`, signals for state, `input()` / `output()`, new control flow, lazy-loaded routes.
- Route params arrive as component inputs (`withComponentInputBinding`).
- **Swap points**: `LogbookRepository` and `ProposalRepository` (both in `core/data-access`, provided in `app.config.ts`), `AuthService` (`core/auth`), `ImageService` (in `features/editor`). The app only knows these abstract classes.
- Stores: root-level for data shared across pages (`LogbooksStore`), component-scoped (`providers: [...]`) for
  state that should die with the page (`EntriesStore`, `EntryAutosave`).
- The editor owns the live document. `RichTextEditor` is keyed by `docKey`; changing the key rebuilds it, which
  also clears undo history so Ctrl+Z cannot cross entries.
- Document schema is defined in one place: `features/editor/extensions/editor-extensions.ts`.
- Permissions are not worked out in the app: every logbook arrives with `myRole`, `canWrite`, `canConfigure` and `canDelete`, decided (and enforced) by the API.
- Saving an entry names the revision it builds on; if someone else saved first the API answers 409 and the entry shows "Changed by someone else" with a Reload button, so nothing is overwritten.

## Sign-in and the API

People sign in with an email and password (`POST /auth/login`, or sign up with `/auth/register`). The API answers with a
token that the app keeps in the browser's local storage until it expires, sends with every request (`authInterceptor`),
and drops when the API stops accepting it, which sends you back to the sign-in page and then to where you were. Sign-up
can be switched off (`AUTH_ALLOW_REGISTRATION=false`). Administrators are the emails in the API's `ADMIN_EMAILS`.

**Where the API is.** The app calls `/api/v1` on its own address. In development `ng serve` forwards `/api` to the
API (`frontend/proxy.conf.mjs`, target `http://localhost:3000`, or `API_PROXY_TARGET`), so there is no CORS to set up.
For a deployment, put the API behind the same address, or set `apiUrl` in `config.json` (next to `index.html`; read at
start-up, so one build runs anywhere):

```json
{ "apiUrl": "https://logbook.example.org/api/v1" }
```

The API must then allow the app's address in `CORS_ORIGINS`.

**GitHub Pages.** The workflow still publishes the app, but the app is only a shell without an API: it shows the
sign-in page and cannot sign anyone in. Point `config.json` at a deployed API to make the Pages site work, or stop deploying it.

## Colours, typography and shadows

- **Colours:** a cyan primary (`#0099dc`: tiles, links, selection) with a navy footer (`#003366`);
  forest green, orange, grass green and purple complete the set. They are defined as CSS variables
  (`--ess-*`) in `frontend/src/styles.scss`, and the Material palettes in `frontend/src/theme/_ess-colors.scss` were generated
  from them with `ng generate @angular/material:m3-theme`. To re-colour the app, change those values and regenerate the palette. **Every colour variable you can use, with its light and dark value, is listed in `frontend/src/theme/COLORS.md`.**
- **Typography:** Titillium Web (open source, bundled with `@fontsource/titillium-web`). Main headlines are
  Light, titles Regular or Semibold, body text Regular.
- **Shadows:** three soft tokens in `frontend/src/styles.scss` (`--app-shadow-sm`, `-md`, `-lg`, plus `-side` for the
  sidebar edge), low-opacity and tinted navy, automatically stronger in dark mode. Use them instead of
  writing new `box-shadow` values.
